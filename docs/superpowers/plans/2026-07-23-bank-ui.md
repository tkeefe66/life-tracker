# Bank / Money UI — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: `superpowers:test-driven-development` for every pure-logic and backend task — write the failing test, run it, watch it fail for the right reason, then implement. Use `superpowers:executing-plans` or `superpowers:subagent-driven-development` to work task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Surface the 992 classified bank transactions that currently exist only behind `GET /api/bank/debug` — as a Money screen answering "what did I actually spend?", a movement breakdown that makes that number credible, and a triage worklist that turns the 62 ambiguous rows into `user_flow` corrections.

**Spec:** `docs/superpowers/specs/2026-07-23-bank-ui-design.md` — read it first; it is the authority on behavior. Its **Open questions** section was closed on 2026-07-23 — see spec §12 Resolved and Task 0 below.

**Architecture:** Same separation the ingestion phase established. `bank_flows.py` gains one more **pure** function (`triage_signature`) — no DB, no I/O. `database.py` gains the triage query and a bulk override writer; it remains the only place with SQL. A new `app/money.py` does DB → domain wiring, the role `app/scorecard.py` plays for the scorecard. `app/routes.py` gains four routes. The frontend gains one screen, one chart component, and a handful of pure helpers in `lib.ts`.

**Tech Stack:** Python 3, FastAPI, pytest; React + Vite, vitest.

## Global Constraints

Copied from the spec and `CLAUDE.md`. Every task's requirements implicitly include this section.

- **`database.py` is the only place with SQL.** No DB calls from `app/`, `jobs/`, or `services/`.
- **`config.py` is the only place that reads `os.environ`.** This feature adds no env vars.
- **`ai_metrics.py` is untouched.** No Claude call is added anywhere in this feature, and no bank field may be added to the `/api/reflection` prompt or to `jobs/weekly_push.py`. Spec §9.
- **Every aggregate resolves through `COALESCE(user_flow, flow)`** — already exposed as `resolved_flow` by `_BANK_TXN_SELECT`. Never read bare `flow` in an aggregate, never re-resolve in Python.
- **Movement totals filter to the outflow side (`amount < 0`) before summing.** A matched transfer is two rows; summing `abs(amount)` over both doubles it. Spec §2.
- **Bank data is not a metric.** No target, no hit/miss, no meter, no streak, no `METRICS` entry, no `--chart-hit` / `--chart-over` semantics, no green/red, no "you're over" language. Spec §1.
- **`bank_flows.py` stays pure and deterministic.** The sync reclassifies the entire table every run and relies on that purity. Do not make `is_ambiguous` or `classify_flow` aware of `user_flow`.
- **The triage query filters `ambiguous = true AND user_flow IS NULL`.** This is the fix for the reappearing-queue trap (spec §6.4) and it lives in SQL, not in `bank_flows`.
- **Charts:** hand-rolled SVG, no library. Wide viewBox, `preserveAspectRatio="xMidYMid meet"`, `width:100%; height:auto`. **Never a fixed pixel height** — that bug has been fixed twice in this repo. The x-axis band lives inside the viewBox.
- **`--chart-bank` is an alias of `--chart-delivery`'s validated values. Do not pick a new hue.** Light `oklch(50% 0.185 277)`, dark `oklch(63% 0.17 277)`.
- **Money formats one way:** `$16.31`, whole dollars trimmed to `$20`, via `money()` in `lib.ts`. Always null-check, never truthiness — a real `$0` must display.
- **Secondary surfaces fail quietly.** A failed fetch hides its section; it never sets a screen-level error that blanks the page.
- **No route returns the access URL or a balance.** Balances are never stored; `config.SIMPLEFIN_ACCESS_URL` is not read by any file this plan touches.
- **Baselines:** `pytest tests/ -v` → **366 passing**. `cd frontend && npm test -- --run` → **50 passing**, then `npm run build`. No commit with a failing check.

### Task 2: Database — triage queries and the bulk override writer

**Files:**
- Modify: `database.py` (bank section, after `set_bank_flow_override`)
- Test: `tests/test_database_bank.py`

**Interfaces:**
- Produces: `db.get_bank_triage(limit)`, `db.get_bank_recently_sorted(limit)`, `db.set_bank_flow_overrides_bulk(simplefin_ids, user_flow)`

- [ ] **Step 1: Write the failing tests** in `tests/test_database_bank.py`. **The second one is the most important test in this feature** — write it first and make sure you understand why it fails:
  - `get_bank_triage` returns a row with `ambiguous = true, user_flow IS NULL`.
  - **The reappearing-queue trap.** Seed an ambiguous row → assert it is in the queue → `set_bank_flow_override(id, "transfer")` → assert it is **not** → now call `set_bank_transaction_derived(id, "spending", None, True)` to simulate the next sync recomputing `ambiguous = true` → assert it is **still not** in the queue. This is spec §6.4. Without the `user_flow IS NULL` predicate the third assertion fails and the queue is uncleanable.
  - Clearing the override (`set_bank_flow_override(id, None)`) returns the row to the queue.
  - `inflow_unknown` rows come back in their own bucket, keyed on `resolved_flow`, so a row whose `flow` is `inflow_unknown` but whose `user_flow` is `income` is absent.
  - Ordering is newest-`posted` first, tie-broken by `simplefin_id` so it is deterministic; `limit` caps each bucket independently.
  - `get_bank_recently_sorted` returns only `user_flow IS NOT NULL` rows, most recently posted first, capped.
  - `set_bank_flow_overrides_bulk(["a","b"], "transfer")` updates both and returns the count; an unknown id in the list is skipped, not an error; an unknown flow raises `ValueError` **before** any write; `None` clears.
- [ ] **Step 2: Run them, watch them fail.** `./venv/bin/python -m pytest tests/test_database_bank.py -q`
- [ ] **Step 3: Implement.** Reuse `_BANK_TXN_SELECT` and `_bank_txn_rows` — do not write a second column list. The triage predicate is `t.ambiguous AND t.user_flow IS NULL`; the inflow predicate is `COALESCE(t.user_flow, t.flow) = 'inflow_unknown'`. `set_bank_flow_overrides_bulk` validates every flow value first, then does all updates inside **one** `_cursor(write=True)` block, mirroring `set_bank_transactions_derived_bulk`'s atomicity rationale. Add a docstring on the triage query explaining the `user_flow IS NULL` predicate — a future reader will otherwise "simplify" it away.
- [ ] **Step 4: Verify** — full pytest run green.
- [ ] **Step 5: Commit** — `feat(db): bank triage queries and bulk flow override`

### Task 3: `app/money.py` — the summary aggregate

**Files:**
- Create: `app/money.py`
- Test: `tests/test_money.py` (create)

**Interfaces:**
- Produces: `money.summary(weeks: int) -> dict`

Shape per spec §10: `covered_from`, `covered_to`, `weeks: [{week_start, spending, partial}]`, `totals: {flow: {count, amount}}`, `spent`, `tracked`, `triage_counts`.

- [ ] **Step 1: Write the failing tests** in `tests/test_money.py`:
  - **Double-count guard:** a matched transfer (`-1000` in account A, `+1000` in account B, both `flow = "transfer"`, same `pair_id`) reports `totals["transfer"]["amount"] == 1000.0`, not `2000.0`, and `count == 2`. Repeat for `card_payment` and `investment`.
  - **Override moves the money:** a `spending` row of $50 with `user_flow = "transfer"` is absent from `spent` and present in the transfer total. Assert `spent` changed, proving the aggregate reads `resolved_flow`.
  - **Weeks before coverage are absent, not zero:** seed one transaction 3 weeks ago, ask for 12 weeks, assert `len(weeks) <= 4` and `weeks[0]["week_start"]` equals the Monday of that transaction's week — there is no zero-height bar for week −11.
  - **Partial flags:** the first week is `partial: true` when `covered_from` is not that week's Monday; the last week is always `partial: true` (it is in progress). A first week that begins exactly on a Monday is not partial.
  - **Empty table** returns `{"covered_from": None, "weeks": [], "totals": {}, "spent": 0, ...}` — shaped, not raising, so the route can be called before the first sync.
  - **`tracked`** is the existing per-service rows for the same window, produced by reusing `app.scorecard`'s helpers — assert a work ride is excluded, so the reuse is real and not a re-derivation.
  - `weeks` clamps 1–52.
- [ ] **Step 2: Run them, watch them fail** with `ModuleNotFoundError: app.money`.
- [ ] **Step 3: Implement `app/money.py`.** One `db.get_bank_transactions_range` call for the window; bucket in Python. Movement totals filter `amount < 0` before summing; `spending` sums `abs(amount)`; `income` sums the positive amounts. Round to 2dp once, at the end, never twice (the `spend()` function's comment about double-rounding drift applies here identically). Derive `covered_from` from the earliest `posted` in the whole table, not the window, so the footnote tells the truth. For `tracked`, call the existing `app.scorecard.spend(weeks)["by_service"]` rather than re-deriving — one source for the tracked figure.

- [ ] **Step 2: Add to the Bank ingestion hard-won facts** the one fact this phase discovered, in the same voice as its neighbours:

> **A triaged row must be excluded by `user_flow IS NOT NULL`, not by clearing `ambiguous`.** `ambiguous` is derived and recomputed from scratch every sync, and `bank_flows.is_ambiguous` reads `flow`, not `resolved_flow` — so a row the user has already ruled on classifies as ambiguous again on the very next run and returns to the queue. Filtering the triage query on `user_flow IS NULL` is the fix: it keeps `bank_flows` pure (which is what lets the sync reclassify the whole table), keeps `ambiguous` meaning "the text looks transfer-ish" rather than "the user hasn't looked at this", and needs no new column.
